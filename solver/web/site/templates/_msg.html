{# The message chip (web-server-guide § Messaging): what wants your attention, and the way to read it. Lives in the fixed header inside `.app-who`, between the terminal and git chips — all three are state about *you* rather than about the page in the pane. There is no messages page, and that is the design. The spool exists so a *command* can tell staff something they must act on (`user` filing a key-authorization request), not so people can write to each other in a browser. So this chip reports, and every verb on it **types a real command into the web shell** — the same move the git chip's verbs and the account page's tool rows make, for the same reason: one execution path, one audit trail, and the command's own `requires()` is the boundary whatever this menu shows. Same
chassis as Actions, git and the user pill: one menu idiom in the header, not four. `msg_spool` (render._context) is the switch: True only on a tier that actually serves /messages, so the auth service — which renders this same header and has no spool — gets the inert chip instead of a dead fetch. It is a plain flag, never a count: the header must not cost a spool read per navigation, so the number and the rows arrive from this element's own fetch a moment later. Two triggers, no polling: · `load` — once per document, so a full page load is always current; · `euler:message from:body` — the delivery nudge, pushed by euler-msg to this user's instance and relayed over the terminal's WebSocket as a TEXT frame (terminal.js → site.js). That is what makes a message arriving *now* show up now. #} {% if subject and msg_spool %}
