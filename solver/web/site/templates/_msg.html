{# The message chip (web-server-guide § Messaging): what wants your attention, and the way to read it. Lives in the fixed header inside `.app-who`, between the terminal and git chips — all three are state about *you* rather than about the page in the pane. There is no messages page, and that is the design. The spool exists so a *command* can tell staff something they must act on (`user` filing a key-authorization request), not so people can write to each other in a browser. So this chip reports, and every verb on it **types a real command into the web shell** — the same move the git chip's verbs and the account page's tool rows make, for the same reason: one execution path, one audit trail, and the command's own `requires()` is the boundary whatever this menu shows. Same
chassis as Actions, git and the user pill: one menu idiom in the header, not four. `msg_spool` (render._context) is the switch: True only on a tier that actually serves /messages, so the auth service — which renders this same header and has no spool — gets the inert chip instead of a dead fetch. It is a plain flag, never a count: the header must not cost a spool read per navigation, so the number and the rows arrive from this element's own fetch a moment later. **This element swaps its CONTENTS, never itself** (`hx-swap="innerHTML"`, and the body lives in `_msg_menu.html`). With `outerHTML` the chip replaced the
on every fetch, and two things broke: the fresh element's own `hx-trigger="load"` fired again, so it re-fetched in a tight loop forever; and each swap reset `open`, so the menu shut a few milliseconds after any click. The git chip never hit this because it has no `load` trigger — it rides the out-of-band swap on each navigation instead. Keeping the element also keeps the `.term-offline` class site.js paints on it. Three triggers, no polling: · `load` — once per document, so a full page load is always current; · `euler:message from:body` — the delivery nudge, pushed by euler-msg to this user's instance and relayed over the terminal's WebSocket as a TEXT frame (terminal.js → site.js). That is what makes a message arriving *now* show up now; · `toggle[this.open]` — opening the panel. The two above are pushes, and a push can be missed: the nudge rides the terminal's WebSocket, so a disconnected or hidden terminal silently drops it, and `load` has not fired since the last full document load. Opening the menu is the one moment a person is *asking* what is waiting, and it is exactly when the answer must not be a count from twenty minutes ago. The filter is what keeps it to opening — a bare `toggle` fires on close too, spending a fetch on a panel nobody is looking at any more. htmx calls the filter with the element as `this` (`r.call(elt, evt)`), so `this.open` reads the state the event just produced. `throttle:1s` because the trigger is a pointer away from being held down: it fires the first open and drops the rest of the second. Nobody reopens a menu inside a second expecting a different number, so it cannot show anything stale a person would notice. #} {% if subject and msg_spool %}
