# __int128

[`__int128`](https://gcc.gnu.org/onlinedocs/gcc/_005f_005fint128.html) is a 128-bit integer
type that [GCC](https://gcc.gnu.org/onlinedocs/gcc/_005f_005fint128.html) and
[Clang](https://clang.llvm.org/docs/LanguageExtensions.html) offer as a compiler extension on
64-bit targets — no header, no library, just `__int128` (signed) and `unsigned __int128`. It is
the C port's answer to a problem Python never has: a native `long long` tops out near
$9.2 \times 10^{18}$, and a great many of these problems produce an intermediate — or a final
answer — that steps just past that line. `__int128` roughly doubles the digit budget to about
$1.7 \times 10^{38}$ signed (and $3.4 \times 10^{38}$ unsigned), which is exactly enough for the
values below, at close to the speed of ordinary machine arithmetic. It recurs because the
Python solution's unbounded `int` hides an overflow that the C translation must actively defend
against, and 128 bits is usually the cheapest defence.

## The idea

There are two distinct jobs `__int128` does, and it helps to keep them apart.

**A transient widening for one multiply.** [Modular exponentiation](https://en.wikipedia.org/wiki/Modular_exponentiation),
[Miller–Rabin](https://en.wikipedia.org/wiki/Miller%E2%80%93Rabin_primality_test) primality, and
[Pollard's rho](https://en.wikipedia.org/wiki/Pollard%27s_rho_algorithm) all reduce to one hot
step: `a * b % m` where `a`, `b`, and `m` all fit in 64 bits but the *product* `a * b` does not.
Reduced operands near a modulus of $10^{10}$ multiply to nearly $10^{20}$, over the 64-bit
ceiling, so the product is computed in 128 bits and immediately reduced back down. Problem 48's
hand-written `mod_pow` is the canonical shape — the wide value never outlives the expression:

```c
result = (__int128)result * base % mod;   /* product held at 128 bits, then reduced to 64 */
base   = (__int128)base * base % mod;
```

One cast is enough: promoting either operand promotes the whole multiply. This is the most common
appearance by far — Problem 97 casts to `__int128` for the same near-$10^{20}$ product in its
[modular exponentiation](https://en.wikipedia.org/wiki/Modular_exponentiation), and the private
number-theory problems that lean on Miller–Rabin or [modular arithmetic](https://en.wikipedia.org/wiki/Modular_arithmetic)
carry the identical `(__int128)x * x % n` idiom inside their inner loop.

**A wider place to keep the answer.** The other job is not transient at all: the result itself is
too big for 64 bits but fits in ~38 decimal digits, so the whole accumulator is widened. Problem
31's [dynamic-programming](https://en.wikipedia.org/wiki/Dynamic_programming) table is declared
`__int128` because a large coin target pushes the count past 23 digits; the DP runs entirely in
128-bit cells and only the final answer is narrowed. A defensive variant of this is to keep a
[continued-fraction](https://en.wikipedia.org/wiki/Continued_fraction) convergent or a running
product in `__int128` throughout — deliberately, because the wide arithmetic is so cheap here —
and narrow to `long long` only at the return.

**The printing gap.** One wrinkle follows from being an extension rather than a standard type: the
`printf` family cannot format a `__int128`, and there is no `INT128_MAX`. When the answer is held
at 128 bits you convert it to a decimal string by hand — repeatedly take the value modulo 10 and
divide, writing digits right-to-left into a buffer. Problem 31 carries exactly such an
`int128_to_str` helper for its final DP cell. Problems 951 and 963 print their 128-bit answers
the same way. The helper is short enough to carry in every port that needs it:

```c
static void print_u128(unsigned __int128 v) {
    char buf[40], *p = buf + sizeof buf;
    *--p = '\0';
    do { *--p = (char)('0' + (int)(v % 10)); v /= 10; } while (v);
    fputs(p, stdout);
}
```

## Five more patterns from the later problems

The later problems use the same two jobs, but they show five refinements worth knowing.

**Widen the accumulator, not the elements.** Often every individual value fits comfortably in
64 bits and only the *running total* crosses the line. In Problem 882 each number's game value,
scaled to fixed point, is a `long long`, but the scaled sum over $10^6$ numbers passes $2^{63}$.
Problem 963's tallies all fit in 64 bits, but the sum of their squares reaches about
$4 \times 10^{20}$. Problem 272's total and Problem 943's subtree counts and sums behave the same
way. So does Problem 297: its Fibonacci terms are `long long`, but the table of
[Zeckendorf](https://en.wikipedia.org/wiki/Zeckendorf%27s_theorem) block sums (the total
term count below each Fibonacci number) passes $2^{64}$, so only that table is
`unsigned __int128`. Widening only the accumulator keeps the tables at 64 bits, which halves their
memory and keeps the inner loops at native speed.

The same split works inside a single memo table. Problem 351 computes the
[totient summatory function](https://en.wikipedia.org/wiki/Euler%27s_totient_function#Other_formulae)
$\Phi(n) \approx 3n^2/\pi^2$ over the quotients $\lfloor n/k \rfloor$. It sieves $\Phi$ at every
value up to about $n^{2/3}$ and memoises the large quotients $n/k$ above that. $\Phi$ passes
$2^{63}$ only past $n \approx 5.5 \times 10^9$, so the sieved prefix, which is the big array,
stays `long long`. Only the few large-quotient entries, about $n^{1/3}$ of them, are `__int128`.

**Widen one squared expression to get an exact floor.** An exact
[floor of an irrational quantity](/topics/technique/floor-and-ceiling-functions) is computed by
squaring: $\lfloor x/\sqrt m \rfloor = \operatorname{isqrt}(\lfloor x^2/m \rfloor)$. The square is
what overflows. Problem 950 runs to $N = 10^{18}$, so its squared terms reach about $10^{36}$:
far past 64 bits, but inside the unsigned 128-bit range of $3.4 \times 10^{38}$. Its floors and
run sums use `unsigned __int128`, and the integer square root starts from a `sqrtl` estimate and
is corrected by exact multiplication. Problem 932
widens a discriminant $(m+1)^2 - 4\,\ell m$ the same way as $m$ approaches $10^{15}$. Problem 255
widens only the single multiply by $2 \times 10^{10}$ in its exact rounding step. Problem 1000
widens a product of three values near $10^9$, which overflows 64 bits even though each factor
is small.

**A wider type doesn't rescue an overflowing formula.** In Problem 951, $\binom{2n}{n}$ fits in
`__int128` up to $n = 65$. The usual multiplicative formula still overflows in its *intermediate*
products well before that. So the C port builds the coefficient from a row of
[Pascal's triangle](/topics/technique/pascals-triangle), using only additions, and no intermediate
ever exceeds the result. The bound you have to prove is on every intermediate, not just the
answer.

**Clear the denominator at 128 bits, divide once, and guard the input.** A
[closed form](/topics/technique/closed-form-expression) with a small rational denominator is
exact only when it is evaluated as one integer numerator followed by one exact division. The
numerator is larger than the quotient by that denominator, so it can overflow even when the
answer fits easily. Problem 276 sums a rounded-quadratic sequence as
$\bigl(k(k+1)(2k+1)/6 + c\bigr)/12$. The cube-sized product is formed in `__int128` before
either division, and the quotient tables of its
[Möbius](https://en.wikipedia.org/wiki/M%C3%B6bius_inversion_formula) sieve are kept at
128 bits too. Problem 957 goes further. Its answer is an O(1) formula in powers of $2^n$ and
$4^n$, signed (some terms alternate with $(-1)^n$ and $(-2)^n$), and scaled by 864 so every
coefficient is an integer. The scaled numerator grows like $11 \cdot 16^n$, so the bound
depends on the *input*. The port therefore does not just assume it fits: it rejects any $n$
outside the range where that numerator provably stays below $2^{127}$, and fails with an error
instead of wrapping. When the width needed depends on the input, check the input at run time,
because a proof made for one size does not cover the rest.

**Unsigned wrap-around can be exact.** Unsigned arithmetic in C is arithmetic modulo $2^{128}$,
which is a ring. A computation built only from addition, subtraction and multiplication therefore
ends on the correct residue, even if intermediates wrap. If the true answer is known to lie in
$[0, 2^{128})$, that residue *is* the answer. Problem 996's C port relies on this for its
unreduced statement examples. It lets the arithmetic wrap modulo $2^{128}$, which is harmless
because the true answers are positive and far smaller. The argument fails the moment a division,
a comparison or a floor touches a wrapped intermediate, so use it only for pure ring arithmetic.

## How to reason about it

Reach for `__int128` in the C port the moment you can show a product or a sum crosses
$9.2 \times 10^{18}$ but stays under ~38 digits — and prove that bound with a back-of-envelope
estimate, not a guess. For the `a * b % m` case the reasoning is standard: two operands each below
$m$ give a product below $m^2$, so any modulus under $2^{63.5}$ (about $1.3 \times 10^{19}$, which
covers every $10^{10}$-scale modulus here) is safe in a 128-bit product. Use `unsigned __int128`
when you need the top bit — a genuine full-width $64 \times 64 \to 128$ product, as in a manual
[bignum](https://en.wikipedia.org/wiki/Arbitrary-precision_arithmetic) multiply — since the
unsigned range reaches $3.4 \times 10^{38}$.

The trade-offs are worth stating plainly:

- **It is not portable to every compiler.** `__int128` is a GCC/Clang extension present only on
  64-bit targets; MSVC has no equivalent. For this project, built with GCC, that is a non-issue,
  but it is the reason the type never appears in portable library code.
- **There is no I/O and no `<limits.h>` constant.** Budget for the hand-rolled decimal conversion
  whenever a 128-bit value has to be *printed*, and hard-code the $1.7 \times 10^{38}$ ceiling if
  you need to bound-check against it.
- **It is a hard ceiling, not arbitrary precision.** 128 bits buys ~38 digits and no more. When an
  intermediate can exceed that — a product of many large factors, a modulus already near $2^{64}$
  whose square overflows even 128 bits — the type silently wraps, and the right move is to switch
  the whole computation to a big-integer library. Several private solutions do exactly this: they
  use the native `__int128` fast path while operands stay below $2^{64}$ and defer to
  [GMP](https://gmplib.org/)'s `mpz_t` above it. If you stay at 128 bits, make the ceiling loud
  rather than silent, as Problem 957's input check does: an error on an out-of-range input is
  far better than a plausible-looking wrong number.

The through-line for the Python author is that none of this machinery exists in the reference
solution — Python's `int` is unbounded, so the overflow is invisible until you translate. Treating
`__int128` as the default first step in C, and reaching past it to a big-integer library only when
38 digits genuinely will not hold, keeps the port both correct and fast.
