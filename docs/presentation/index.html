The story behind the solver

Every feature began as a problem I ran into.

  1. Keep private solutions private, in a public repository

    Encrypted strings in the codeneeded its own loader Encrypted .enc fileschecked out, checked back in A git filterplain text at work, ciphertext in git

  2. Keep the key safe, and don't lose it (I did, more than once)

    Every machine holds its own sealed copy, and any holder can pass it on, whole or in two halves.

  3. Do the old solutions still work after an update?

    Each keeps its test cases and answer; one line re-checks them all: loop {solved}: eval {loop.number}

  4. A new machine: GitHub holds the code, not the setup

    One command builds the rest: make install-all, from system packages to git hooks.

  5. Code that stays right, and can be rewritten

    mypy and flake8 on every commit, autoflake to tidy; and when the framework changed (the runner, the decorators, solve()'s signature), code transformers rewrote every solution.

  6. Turn solutions into knowledge

    An explanation beside every solution, tags by technique, articles linking problems, and a website to read them.

Space highlights one row at a time. The left side is the problem as I met it; the right is what the solver does about it now.

Encryption went through three designs. Encrypting strings inside the code needed a custom loader to run anything. Encrypted .enc files beside the code needed a checkout and check-in step, and a lock to go with it. Now a git filter encrypts on the way into git and decrypts on the way out, so I never see ciphertext while I work.

The key: I lost it more than once. Now each machine keeps its own copy, sealed to that machine's key; any holder can issue it to another machine (key-export, or over the message spool), or split it in two halves (key-split, key-reconstruct) so no single message carries all of it.

Old solutions: every solution has test cases with recorded answers, so after a package upgrade one loop re-runs them all. The runner gives every solution the same contract, which is what makes that loop possible.

A new machine: a one-line install script clones the repository and runs make install-all, which sets up the system packages, the Python environment, git hooks, tab completion, Chrome and Claude Code. Secrets stay outside the repository, in ~/.euler.

Code quality: every commit passes mypy and flake8 (the git hooks refuse otherwise), and autoflake, isort and black tidy each new solution. Transformability: the framework changed shape more than once (the runner, the decorators, the signature of solve()), and each time I wrote code transformers that rewrote every existing solution rather than editing hundreds by hand. Consistent code is what makes that possible.

Knowledge: the explanations, tags and articles are counted on the previous slide.

@runner.main
def solve(*args: str) -> str:
    """Sieve of Sundaram over [1, n·ln n] …"""
    n = runner.parse_int(args[0])
    if n == 1:
        return str(2)
    max_expected_value = int(n * math.log(n))
    numbers = list(range(0, max_expected_value + 1))
    for i in numbers[1:]:
        for j in range(i, max_expected_value + 1):
            try:
                numbers[i + j + 2 * i * j] = 0
            except IndexError:
                break
    return str(2 * [i for i in numbers if i != 0][n - 2] + 1)

A real regression, found while migrating old solutions onto the runner: tables and caches built at module level were excluded from the first run's timing and free after it, so benchmarks understated the real cost. The rule now: build them inside solve(), sized to the input. The examples here are illustrative, not from a private solution.

One decorator per command

  

    
packages/solver/solver/core/git.py
@register(requires='contributor', aliases=('commit',),
          quietable=True)
def git_commit(
    problem: Problem,
    *targets: Literal['solution', 'solutions', 'docs',
                      'topics', 'update'],
    message: Annotated[str, Ask('Message', when=_is_not_amend,
                                multiline=True)] = '',
    amend: bool = False,
    reset: bool = False,
) -> int:
    """Stage and commit the named targets — the one commit verb."""

      
    
        
  • git_commit becomes git-commit; requires sets the lowest profile allowed.
    • 
        
  • problem: Problem takes a bare number or {next}, remembers it as the current problem, and fills it in when left out.
    • 
        
  • *targets: Literal[…]: any number of choices, checked and tab-completed.
    • 
        
  • Annotated[str, Ask(…)]: left out, the shell asks for it, but only when it applies (an amend keeps its message).
    • 
        
  • A bool becomes a flag; the return value is the exit code.

The signature is reformatted to fit the slide; the code is packages/solver/solver/core/git.py's git_commit. Functions stay plain Python: the decorator registers them, it doesn't transform them. Only one function in register.py knows about Annotated: it lifts the Ask out and hands everything else the plain type. Ask appears in 28 places in the codebase.
The problem parameter is the same current problem the {problem} variable holds on the previous slide, which is why eval alone re-runs the active problem. The docstring is the help text and the source of the generated docs; check-commands holds every docstring to one standard.

Designs I built and threw away

  

    
Brokers for secrets
Services that held the API and git keys on behalf of a shared web user. One was built and working. Dropped once giving every collaborator their own user removed the need.

    
A checkout lock
A second lock on top of the workspace's own. It worked as designed and confused everyone, so it was reverted.

    
One shared key file
Every machine's sealed key in one tracked file: a long run of merge conflicts. Now each machine keeps its own.

    
Versions from git tags
Build-time version detection from git. Replaced by one tracked version.py that only the release script writes.

  

  
Audiences remember this slide. The theme: the simpler design usually won, and removing a constraint beat working around it.
